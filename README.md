# KivoPlayer Sync Server

Серверная часть системы синхронизации музыкальной библиотеки **KivoPlayer** между устройствами.

Проект предназначен для хранения музыкальных файлов и текстов песен (LRC), а также для последующей синхронизации локальной музыкальной библиотеки пользователя между компьютерами и другими устройствами.

> ⚠️ **Проект находится на начальной стадии разработки (Early Development).**
>
> Базовая система синхронизации уже реализована, однако в текущей версии присутствуют ошибки и нестабильность при синхронизации файлов. Сервер пока не предназначен для production-использования.

## О проекте

**KivoPlayer Sync Server** является отдельным серверным компонентом экосистемы Kivo Apps и используется совместно с локальным музыкальным плеером **KivoPlayer**.

Основная идея проекта — предоставить пользователю собственный сервер, который позволяет синхронизировать музыкальную библиотеку между устройствами.

Вместо того чтобы каждый клиент хранил полностью независимую библиотеку, устройства смогут обращаться к серверу для проверки наличия файлов, загрузки отсутствующих треков и сохранения текстов песен.

В дальнейшем проект планируется развить от простого файлового хранилища до полноценной системы синхронизации **структуры музыкальной библиотеки пользователя**.

## Основная идея

Упрощённо взаимодействие выглядит следующим образом:

```text
                    ┌──────────────────────┐
                    │   KivoPlayer / PC    │
                    │                      │
                    │  Local Music Library │
                    └──────────┬───────────┘
                               │
                               │ Sync
                               ▼
                    ┌──────────────────────┐
                    │ KivoPlayer Sync      │
                    │ Server               │
                    │                      │
                    │  Audio files         │
                    │  Lyrics              │
                    │  File metadata       │
                    │  Library structure   │
                    └──────────┬───────────┘
                               │
                               │ Sync
                               ▼
                    ┌──────────────────────┐
                    │ Other Device         │
                    │                      │
                    │ Local Music Library  │
                    └──────────────────────┘
```

На текущем этапе сервер в основном работает с самими файлами и их fingerprint'ами.

В будущем система должна учитывать также расположение файлов внутри музыкальной библиотеки.

## Возможности

На текущем этапе реализована базовая инфраструктура:

- проверка наличия треков на сервере;
- загрузка аудиофайлов;
- скачивание аудиофайлов;
- загрузка LRC-файлов;
- скачивание LRC-файлов;
- идентификация файлов с помощью fingerprint;
- Docker-развёртывание;

Часть функциональности всё ещё находится в разработке и может работать нестабильно.

## Синхронизация файлов

Для определения состояния библиотеки используется fingerprint файла.

Клиент передаёт серверу информацию о файле, после чего сервер определяет, существует ли соответствующий ресурс.

Упрощённый сценарий:

```text
Local Library
      │
      ▼
Calculate fingerprint
      │
      ▼
POST /api/sync/check
      │
      ├── File exists
      │       │
      │       └── Nothing to upload
      │
      └── File missing
              │
              └── Upload file
```

В будущем алгоритм синхронизации будет значительно расширен.

### Текущее состояние

Сейчас синхронизация находится в процессе разработки.

В частности, существуют проблемы, связанные с некоторыми сценариями загрузки и скачивания файлов. Поэтому текущую реализацию следует рассматривать как экспериментальную основу для дальнейшего развития системы.

## Fingerprint

Для идентификации аудиофайлов используется fingerprint.

Это позволяет не зависеть только от имени файла:

```text
song.mp3
```

и определять файл по его содержимому/идентификатору.

В будущем fingerprint также будет использоваться совместно с метаданными и информацией о расположении файла.

## API

Основные API endpoints:

### Health Check

```http
GET /health
```

Проверка состояния сервера.

### Проверка синхронизации

```http
POST /api/sync/check
```

Используется клиентом для определения состояния файла на сервере.

### Загрузка трека

```http

```

### Получение трека

```http
GET /api/tracks/:audio-fingerprint
```

Скачивание аудиофайла с сервера.

```http
POST /api/tracks/:audio-fingerprint/lyrics/:lrc-fingerprint
```

Загрузка LRC-файла для определённого трека.

### Получение текста

```http
GET /api/tracks/:audio-fingerprint/lyrics/:lrc-fingerprint
```

Скачивание LRC-файла.

API будет изменяться по мере развития системы.

## Будущее развитие синхронизации

Одним из основных направлений дальнейшей разработки является сохранение **относительных путей файлов**.

Сейчас сервер в первую очередь рассматривает музыкальную библиотеку как набор файлов:

```text
Song A
Song B
Song C
Song D
```

В дальнейшем сервер должен учитывать и структуру каталогов:

```text
Music/
├── Anime/
│   ├── Artist A/
│   │   ├── Song 1.flac
│   │   └── Song 2.flac
│   │
│   └── Artist B/
│       └── Song 3.mp3
│
├── Rock/
│   └── Artist C/
│       └── Album/
│           └── Song 4.flac
│
└── Electronic/
    └── Artist D/
        └── Song 5.mp3
```

Для этого планируется сохранять **относительный путь файла внутри музыкальной библиотеки**, а не абсолютный путь конкретного компьютера.

Например:

```text
Music/
└── Anime/
    └── Artist/
        └── Song.flac
```

может быть представлен на сервере как:

```text
Anime/Artist/Song.flac
```

При этом абсолютный путь вроде:

```text
C:\Users\User\Music\Anime\Artist\Song.flac
```

не должен быть привязан к серверу, поскольку на другом устройстве библиотека может находиться в совершенно другом месте.

### Зачем это нужно

Сохранение структуры библиотеки позволит в будущем:

- восстанавливать структуру папок при синхронизации;
- сохранять расположение треков между устройствами;
- автоматически создавать плейлисты на основе каталогов;
- группировать музыку по папкам;
- синхронизировать отдельные каталоги;
- использовать структуру файлов для дополнительной логики плеера;
- восстанавливать библиотеку после переустановки системы или переноса на другой компьютер.

Таким образом, конечная концепция синхронизации должна развиваться от:

```text
"Синхронизировать файлы"
```

к:

```text
"Синхронизировать музыкальную библиотеку
вместе с её структурой"
```

Это позволит использовать сервер не только как файловое хранилище, но и как источник состояния музыкальной библиотеки пользователя.

## Управление файлами

В будущем планируется добавить полноценное управление файлами на сервере.

В частности:

- удаление файлов с сервера;
- удаление LRC-файлов;
- определение неиспользуемых файлов;
- синхронизация удалений;
- более точное сравнение состояния клиента и сервера.

Например, если пользователь удалил трек из своей основной библиотеки, сервер в дальнейшем сможет определить это изменение и предложить или выполнить удаление соответствующего файла на сервере.

Механизм удаления будет реализован после стабилизации базовой синхронизации.

## Импорт музыкальной библиотеки

Параллельно с сервером разрабатывается отдельный скрипт для автоматизации импорта музыки.

Предполагаемый сценарий:

```text
Downloads
    │
    ▼
Найден новый аудиофайл
    │
    ▼
Определение информации о треке
    │
    ▼
Перемещение в Music Library
    │
    ▼
Поиск текста песни
    │
    ├── Текст найден
    │       │
    │       ▼
    │     Сохранение LRC
    │
    └── Текст не найден
            │
            ▼
        Пропуск / повторный поиск
```

Основная задача скрипта — уменьшить количество ручных действий при добавлении новой музыки.

После появления нового аудиофайла в Downloads скрипт сможет автоматически:

1. определить музыкальный файл;
2. определить информацию о треке;
3. перенести его в папку музыкальной библиотеки;
4. определить предполагаемое расположение файла;
5. попытаться найти текст песни;
6. сохранить найденный LRC;
7. в дальнейшем передать информацию в систему синхронизации.

В перспективе импортёр может стать отдельной частью общей экосистемы KivoPlayer.

## Запуск

### Требования

Необходимо установить:

- Go 1.26+
- Docker
- Docker Compose

### Docker Compose

Для запуска проекта:

```bash
docker compose up -d
```

После запуска сервер будет доступен на:

```text
http://localhost:8000
```

Проверить состояние можно через:

```http
GET /health
```

Ожидаемый результат — успешный ответ сервера.

### Локальный запуск

Для запуска без Docker необходимо настроить подключение к PostgreSQL и переменные окружения.

После этого:

```bash
go run ./cmd/server
```

## Связь с KivoPlayer

Sync Server является серверной частью экосистемы **KivoPlayer**.

Основной клиент — локальный музыкальный плеер для компьютера, который работает с собственной музыкальной библиотекой пользователя.

Клиент отвечает за:

- воспроизведение музыки;
- работу с локальной библиотекой;
- отображение обложек;
- работу с LRC;
- визуализацию;
- поиск;
- рекомендации;
- взаимодействие с Sync Server.

Sync Server отвечает за:

- хранение файлов;
- хранение текстов;
- проверку наличия ресурсов;
- передачу файлов между устройствами;
- синхронизацию библиотеки.
